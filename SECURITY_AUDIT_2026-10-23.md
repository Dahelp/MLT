# Отчёт по безопасности MLT

Дата: 23 октября 2026 года. Объект: исходники сайта и API, зависимости, Apache-конфигурация и процесс публикации `mlt-lifestyle.com`.

## Вывод

Обнаружены и исправлены существенные недостатки авторизации, защиты API и публикации. Первоначальный аудит зависимостей дал 85 записей: 6 critical, 42 high, 29 moderate, 8 low. После обновления осталась одна запись high в инструменте разработки `braces`. Затем для неё подготовлен и подключён собственный патч ограничения глубины; опубликованного upstream-исправления пока нет, поэтому сканер продолжает выдавать предупреждение по версии пакета. Это число записей advisory, а не число подтверждённых способов взломать работающий сайт.

Заявлять, что устранены все возможные уязвимости или достигнута абсолютная безопасность, оснований нет. Ниже отдельно перечислены выполненные изменения и оставшиеся ограничения.

## Что проверено

- PHP API: учётные записи, роли сотрудников, клиентские заказы, каталог, загрузка изображений, чаты, инвестиции, платежи и ваучеры.
- Сопоставление прав в интерфейсе и серверных обработчиках; выборочные негативные проверки доступа через локальные HTTP-тесты.
- Обработка JSON, методы запросов, размеры тела, Origin, ограничение частоты запросов и раскрытие ошибок.
- Apache: доступ к служебным файлам, выполнение файлов в uploads, HTTPS и защитные заголовки.
- Прямые и транзитивные npm-зависимости, конфигурация GitHub Actions и канал передачи файлов.
- Безопасные HEAD-запросы к действующему сайту и проверка FTPS/TLS без входа в аккаунт хостинга.

Проверка не включала эксплуатацию уязвимостей на production, нагрузочную атаку, реальные списания, просмотр персональных данных клиентов или изменение production-базы.

## Найденные риски и исправления

| Приоритет | Находка | Изменение |
| --- | --- | --- |
| Высокий | В исходниках находились хеши стартовых паролей и автоматическое создание служебных аккаунтов | Удалено создание аккаунтов по встроенным паролям. При подключении к БД отключаются три прежних стартовых хеша и связанные с ними сессии. Индивидуально заменённые пароли не затрагиваются |

## Проверки, которые уже существовали

В просмотренных обработчиках используются подготовленные SQL-запросы для пользовательских значений, случайные токены с хранением хеша в БД и серверные проверки ролей. Загрузка каталога проверяет MIME через finfo и использует случайное имя WebP/AVIF. Stripe webhook проверяет подпись и временное окно. Платёжные обработчики PHP получают сумму из сохранённого заказа, а не доверяют цене браузера.

Это результаты просмотра конкретных участков и тестов, а не доказательство отсутствия SQL injection, XSS, IDOR или ошибок платёжной логики во всём приложении.

## Ограничения и дальнейшее усиление

1. **Осталась advisory `braces` high:** `GHSA-vfj7-8cjw-p6xm`, stack-exhaustion DoS на глубоко вложенных glob-шаблонах. Используется транзитивно в ESLint и сборке Vinext. Исправленная версия не опубликована. В просмотренном приложении не найден путь передачи клиентского glob в этот инструмент; это ограничивает практическую применимость, но не отменяет находку. Добавлен локальный патч `patches/braces@3.0.3.patch`: ограничена глубина парсера и рекурсивных обходов compile, expand, stringify, включая прямые AST-входы. Он автоматически применяется через patchedDependencies и проверяется отдельными регрессионными тестами до сборки. Не подавлять находку в аудите; после выхода upstream-исправления проверить его и заменить локальный патч. Подробности — в SECURITY_PATCHES.md.
2. **MFA сотрудников не внедрена.** Дополнительный приоритет — MFA либо внешний шлюз доступа для административных панелей. Сейчас остаётся парольная авторизация с серверными проверками ролей и ограничением перебора.
3. **Токены интерфейса хранятся в localStorage.** XSS в том же origin может получить токен. Переход на HttpOnly Secure cookies потребует отдельной согласованной миграции входа и CSRF-защиты всех интерфейсов.
4. **CSP пока ограничивает отдельные возможности, но не scripts.** В статических страницах есть inline-скрипты гидратации; для полноценного script-src нужны хеши при экспорте либо nonce при динамической отдаче с проверкой карт и платежей.
5. **Не проверены настройки панели хостинга:** версии и патчи production PHP/Apache/ОС, права файлов и пользователя БД, резервное копирование и восстановление, сетевой firewall, журналы доступа и WAF/DDoS. Для этого нужен доступ к инфраструктуре. Файловый лимитер приложения не заменяет защиту на сетевом периметре.
6. **Подтверждение email не реализовано.** Автоматическое получение старых заказов по email отключено. Гостевые заказы следует привязывать после проверки владельца через администратора или отдельный механизм подтверждения почты.
7. **Выход в интерфейсе удаляет локальный токен.** Общая серверная ревокация при выходе ещё не внедрена; остаточное окно для ранее скопированного токена ограничено временем его серверной сессии.
8. **Смена секретов инфраструктуры не выполнялась.** Если FTP-пароль передавался через недоверенные сети до перехода на FTPS, его следует заменить в панели хостинга и GitHub Secrets; также рекомендуется проверить историю доступа.

## Последствия для пользователей

- Служебные аккаунты, у которых сохранились три прежних стартовых пароля, больше не смогут войти до назначения нового пароля администратором. Действующие индивидуальные пароли сохраняются.
- Новые входы создают сессию на сутки. Обычные ранее выданные сессии сохраняют прежнюю дату истечения; сессии отключённых стартовых аккаунтов отзываются при подключении приложения к БД.
- Старые гостевые заказы без `user_id` не отображаются автоматически по совпадению email. Это сознательное закрытие обхода проверки владельца.
- Локальные Vinext-маршруты без PHP больше не инициируют платежи и не отправляют заявки альтернативным путём. Для этих операций требуется рабочий PHP backend.

## Исправление совместимости карты

Глобальный no-referrer мешал загрузке тайлов OpenStreetMap: сервис требует корректный Referer и возвращал изображения блокировки 403. Политика публичных страниц изменена на strict-origin: передаётся только origin, без пути страницы и query-параметров; при переходе с HTTPS на HTTP адрес не передаётся. Для всех PHP-ответов, включая API и платёжные callbacks, сохранён no-referrer. Apache-регрессионный тест проверяет обе политики. Требование провайдера: https://operations.osmfoundation.org/policies/tiles/.
