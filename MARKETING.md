# Кабинет маркетолога

Маршрут `/marketing/`, роль `marketer`. Администратор назначает её в «Пользователи» и может открыть кабинет через «Маркетинг» или «Команда и доступ». Реальный аккаунт маркетолога автоматически не создаётся. Доступ администратора не меняет смысл или состав отчётов.

## Контракт данных

`POST /api/marketing.php`, JSON `{ "action": "overview", "days": 30 }`. Допустимы только 30, 90 и 365. Другие поля, действия, периоды и произвольные фильтры отклоняются. Сервер проверяет действующую сессию и роль `marketer`/`admin` до чтения отчётов. Ответы не кешируются. API не меняет бизнес-записи и не вызывает платёжные, Telegram или почтовые сервисы. Общая `mlt_db` сохраняет существующее поведение инициализации схемы проекта.

Период `[start, endExclusive)` — завершённые календарные дни базы сайта, без сегодняшнего дня. Это согласовано с существующими записями `NOW()`; UTC для исторических записей не предполагается. Заявки учитывают архив, чтобы архивирование не меняло историю привлечения. Статусы и оплаченные суммы отражают текущее состояние выбранной когорты, а не исторический статус на конец периода.

| Сводка | Источник и правило |
| --- | --- |
| Заявки, коллекции, статусы, месяц создания | `mlt_orders`, дата создания; только фиксированные категории, неизвестные строки → `other` |
| Заявки с оплатой | `paid_amount > 0`, включая кредит ваучера; не количество транзакций |
| Заявка → оплата | Заявки с положительной оплаченной суммой / все заявки выбранного периода; не конверсия сайта |
| Средняя и сгруппированная длительность | Положительный `travel_days`, группы 1–7 / 8–14 / 15+; пустые значения не считаются нулём |
| Регистрации по языкам | `mlt_users`, только `traveller`/`agency`, по дате создания аккаунта; язык не национальность и не география |
| Коммерческие обращения | `mlt_commercial_inquiries`, по дате создания; `listing_ID_*` объединяются с `acquisitions`, `investments` отдельно; источник формы не рекламный источник |
| Новые чаты | Метаданные `mlt_chat_conversations`, дата создания и отдел; сообщения не читаются |
| Карточки локаций | `mlt_scout_submissions`, дата создания и текущий статус модерации; без автора и координат |
| Поступления за путешествия | `mlt_payments`, дата записи платежа, `status=paid`, `provider=stripe/paypal`, отдельно по валютам; без кредита ваучеров |
| Ваучеры | `mlt_voucher_purchases`, дата `paid_at`, только `paid`; сумма `price_cents * quantity` и число единиц |

Поступления не являются прибылью или чистой выручкой. В реестре нет полной модели возвратов/комиссий; ручное исправление `paid_amount` не становится автоматически подтверждённой транзакцией. Ваучеры показаны отдельно, без повторного суммирования их погашения с поступлениями. Конверсию коммерческого обращения в продажу не рассчитываем: у обращений нет надёжного статуса сделки или связи с оплатой.

## Границы доступа

Сервер возвращает только разрешённые агрегаты. Нет сырых записей, клиентских идентификаторов, контактов, имён клиентов, маршрутов, точных дат поездок, свободных текстов, переписки, платёжных идентификаторов, кодов ваучеров, документов, паролей или секретов. Единственное имя — собственное имя вошедшего сотрудника для стандартной панели.

Группы 1–4 скрываются. Если одна ячейка мала, скрывается вся соответствующая разбивка, чтобы итог и другие ячейки не раскрывали её вычитанием. Конверсия требует достаточного числа оплативших и неоплативших заявок; средняя длительность — минимум пяти записей. Для сумм поступлений нужны минимум пять разных заявок на валюту; для ваучеров — пять разных покупателей. Это ограничение раскрытия малых групп, а не доказательство полной анонимности: несколько записей могут принадлежать одному клиенту. Произвольная сегментация, точные даты и сырой экспорт не предоставляются.

Нулевой результат, скрытая малая группа, отсутствующая таблица необязательного модуля и ошибка базы различаются. Ошибка чтения не превращается в нулевую статистику. Изменения ролей используют существующее аннулирование сессий в `admin-users.php`.

## Визуальные и поведенческие владельцы

Канонический визуальный контракт — `STYLE_GUIDE.md`, значения шрифтов и радиусов — `app/globals.css`. Общий каркас, меню, язык, сворачивание и мобильная навигация — `OperationsShell`, `OperationsSidebar`, `OperationsTopbar`, `useOperationsLocale`. Панели используют `--staff-panel-*` из `operations-shell.css`, согласованные с существующей `.concierge-table`. Локальные псевдоэлементы и новые UI-библиотеки не добавляются. Списки, даты и формы ввода в новом кабинете не нужны: выбор периода — обычные кнопки с `aria-pressed`, сохранённый в URL.

В кабинете нет уведомлений и обращений к API с клиентскими реестрами. Все три языка служебных кабинетов поддерживаются: EN/DE/RU. Загрузка, отмена устаревшего запроса, таймаут, отсутствие данных, скрытые данные, ошибка, 401/403 и повторная загрузка обрабатываются отдельно. Числа предыдущего периода не показываются под новым выбранным периодом.

Описание границ доступа остаётся в этом контракте и серверной политике, а не отдельной панелью на рабочем экране. Статусы недоступных источников сохраняются рядом со сводками.

При входе через `/account/` и восстановлении сессии перед переходом в служебный кабинет применяется язык профиля сотрудника: EN/DE/RU, для остальных языков — EN. Сохранённый язык другого аккаунта в браузере не имеет приоритета. Ручное переключение в верхней панели действует при дальнейшей работе и перезагрузке кабинета; повторный вход снова применяет язык профиля.

## Проверки

- `node --test tests/marketing-api.test.mjs tests/admin-users-api.test.mjs tests/operations-access.test.mjs tests/operations-navigation.test.mjs tests/operations-bootstrap.test.mjs`
- `node tests/marketing.browser.mjs` — локальный предпросмотр, вымышленные ответы API, 1440/390 px, EN/DE/RU, состояния загрузки/пустоты/малых групп/ошибки/401/403, восстановление, клавиатура и мобильное меню.
- `pnpm test` — обязательная сборка и общие проверки проекта.

Для браузерной проверки используются существующие `MLT_PLAYWRIGHT_MODULE`, `MLT_BROWSER_EXECUTABLE`, `QA_BASE`. Реальная база клиентов не используется.
